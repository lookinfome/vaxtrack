TASK 1 — UserCredentials Soft-Delete (edge case handling)
────────────────────────────────────────────────────────────────────────────────

Problem:
  When a user account was soft-deleted, the UserCredentials row was left
  untouched. This permanently locked the email address — no one could ever
  register again with that email.

What was done:
  - Added IsDeleted (bool, default false) and DeletedAt (DateTime?) to
    UserCredentialsModel.cs
  - Added SoftDeleteCredentialsByUserUidAsync(string userUid) to
    IUserCredentialsRepository and UserCredentialsRepository.
    On delete: sets IsDeleted = true, DeletedAt = now, clears PasswordHash
    (security hygiene — a deleted account's hash has zero purpose).
  - Updated all three Get methods in UserCredentialsRepository to filter
    !c.IsDeleted: GetCredentialsByEmailAsync, GetCredentialsByUserUidAsync,
    GetCredentialsByUserUidsAsync.
  - Updated UserService.DeleteUserAsync to cascade credentials soft-delete
    after revoking role mappings.
  - Extracted private ExecuteUserDeleteCascadeAsync(UserModel) helper so the
    same cascade logic is reused by both DeleteUserAsync and DeleteMyAccountAsync.
  - EF migration: AddUserCredentialsSoftDelete — applied to database.

Why PasswordHash is cleared:
  After an account is deleted, the hash has no legitimate use. Keeping it is a
  liability if the database is ever compromised (hash could be brute-forced
  offline). Email is kept for audit trail.

Why not hard-delete:
  Inconsistent with every other entity's soft-delete pattern in the codebase.
  Loses audit trail and makes accidental deletion unrecoverable.

Login protection after deletion (double-gated):
  Step 1 — GetCredentialsByEmailAsync now filters !IsDeleted → returns null.
  Step 2 — GetUserDetailsByUserUidAsync filters !IsDeleted on Users table.
  Both gates independently block login for deleted accounts.

TASK 2 — Duplicate Email Check on Registration (Gap 1)
────────────────────────────────────────────────────────────────────────────────

Problem:
  Two different users could register with the same email because
  CreateUserAsync never checked whether the email was already taken.

What was done:
  - In UserService.CreateUserAsync, added a check before saving the user:
    calls GetCredentialsByEmailAsync(email) — if a record is found (active,
    not soft-deleted), throws with "email is already in use".
  - No DB-level unique constraint added (would conflict with the soft-delete
    design where deleted rows keep their email for audit). The check is
    service-layer only, which is sufficient since the filter already excludes
    deleted rows.

TASK 3 — Email Update Endpoint (Gap 2)
────────────────────────────────────────────────────────────────────────────────

Problem:
  No mechanism existed to change the email address after registration.
  Email is stored in UserCredentials, not UserModel, so the existing
  UpdateUserAsync couldn't touch it.

What was done:
  New DTOs:
    - UpdateEmailRequestDto: UserId, NewEmail, CurrentPassword
    - UpdateEmailResponseDto: UserId, NewEmail, UpdatedAt

  New repository method (IUserCredentialsRepository + UserCredentialsRepository):
    - UpdateEmailAsync(string userUid, string newEmail): finds active
      credentials by UserUid, updates Email field, saves.

  New service method (IUserService + UserService):
    - UpdateEmailAsync(UpdateEmailRequestDto, callerUserUid, callerIsAdmin):
      1. Fetch user by UserId → get UserUid.
      2. Ownership check: caller must own the account or be admin.
      3. Non-admin callers must supply correct CurrentPassword (BCrypt.Verify).
         Admin callers skip this — they can override without knowing the password
         (support / account recovery use case).
      4. New email must not already belong to another active account.
      5. Calls UpdateEmailAsync on the credentials repository.

  New endpoint (UserController):
    - PUT /api/vaxtrack/v1/user/updateemail
    - [Authorize] — any authenticated user (ownership enforced in service)
    - Returns 403 Forbid if caller does not own the account

TASK 5 — Ownership Checks Across All Endpoints (Gap 4)
────────────────────────────────────────────────────────────────────────────────

Problem:
  Any authenticated user could view, update, or cancel any other user's data
  simply by knowing the target UserId or BookingId. No identity-based access
  control existed beyond the admin vs. user role split.

Design:
  JWT token stores sub = UserUid (GUID). Controllers extract:
    - CallerUserUid: User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value
    - CallerIsAdmin:  User.IsInRole("admin")
  These are passed to service methods. Services throw UnauthorizedAccessException
  if the check fails. Controllers catch UnauthorizedAccessException and return
  403 Forbid.

Changes to IUserService + UserService:
  - UpdateUserAsync: callerUserUid + callerIsAdmin added. After fetching the
    user, checks foundUser.UserUid == callerUserUid (or admin).
  - GetUserProfileDataAsync: same ownership check. A user cannot view another
    user's profile (prevents PII harvesting).

Changes to IBookingService + BookingService:
  - CreateBookingAsync: callerUserUid added. Checks dto.UserUid == callerUserUid.
    Prevents booking on behalf of someone else.
  - BookDose2Async: callerUserUid added. Ownership now validated against JWT sub
    claim, not against the client-supplied UserUid in the DTO (old approach was
    exploitable if an attacker sent a forged UserUid in the request body).
  - CancelBookingsAsync: callerUserUid + callerIsAdmin added. Fetches booking,
    checks booking.UserUid == callerUserUid (or admin).
  - GetBookingByBookingIdAsync: same ownership check.
  - GetBookingsByUserIdAsync: userId param (UserUid) must match callerUserUid
    (or admin). Prevents viewing another user's booking history.

UpdateBookingAsync restricted to admin:
  This method allows overriding all booking fields including dose completion
  flags and timestamps — a regular user should never be able to mark their own
  dose as "completed". Moved to [Authorize(Roles="admin")] in BookingController.

Controller changes (UserController + BookingController):
  - Added CallerUserUid and CallerIsAdmin private helpers.
  - All affected action methods now pass these into service calls.
  - All affected action methods now catch UnauthorizedAccessException → Forbid().

TASK 6 — Self-Delete Endpoint (Gap 5)
────────────────────────────────────────────────────────────────────────────────

Problem:
  A normal user had no way to delete their own account. DeleteUserAsync was
  [Authorize(Roles="admin")] only.

What was done:
  New service method (IUserService + UserService):
    - DeleteMyAccountAsync(string callerUserUid): looks up user by UserUid
      (from JWT, not a URL param), then delegates to
      ExecuteUserDeleteCascadeAsync — same cascade as admin delete:
        1. Soft-delete user profile.
        2. Soft-delete all bookings → restore pending hospital slots.
        3. Revoke all role mappings.
        4. Soft-delete credentials → clear PasswordHash.

    - DELETE /api/vaxtrack/v1/user/deletemyaccount
    - [Authorize] — any authenticated user, no role restriction
    - No URL parameter — account identified entirely from JWT sub claim
    - Admin keeps their own DELETE /user/deleteuser/{userId} endpoint

TASK 7 — Logout and Token Blacklist (Gap 6)
────────────────────────────────────────────────────────────────────────────────

Problem:
  JWT is stateless — there was no way to "logout." A stolen or expired-but-
  not-yet-expired token remained usable with no server-side revocation.

Design chosen:
  Token blacklist in SQL Server (RevokedTokens table). Each revoked token's
  JTI (JWT ID claim) is stored. On every authenticated request the OnTokenValidated
  hook checks the blacklist — if the token's JTI is found, the request is
  rejected even if the token's signature and expiry are otherwise valid.
  Opportunistic cleanup: expired blacklist rows are pruned on each logout call
  so the table stays small without a background job.

Why JTI (not the full token):
  JTI is a short, unique string. Storing the full token string is wasteful and
  unnecessarily exposes sensitive data.

New files:
  - Models/RevokedTokenModel.cs: Id, Jti, ExpiresAt, RevokedAt
  - Interfaces/RepositoryInterfaces/ITokenBlacklistRepository.cs:
      RevokeTokenAsync(string jti, DateTime expiresAt)
      IsRevokedAsync(string jti) → bool
  - Repositories/TokenBlacklistRepository.cs: full implementation with
    opportunistic cleanup of expired rows on each revocation.

Changes to IAuthService + AuthService:
  - Added LogoutAsync(string jti, DateTime expiresAt).
  - AuthService injects ITokenBlacklistRepository.
  - LogoutAsync validates jti is non-empty, then calls RevokeTokenAsync.

New endpoint (AuthController):
  - POST /api/vaxtrack/v1/auth/logout
  - [Authorize] — must be authenticated to logout
  - Extracts jti from User.FindFirst(JwtRegisteredClaimNames.Jti)
  - Extracts expiresAt from User.FindFirst(JwtRegisteredClaimNames.Exp)
    (Unix timestamp → UtcDateTime conversion)
  - Returns 200 { message: "logged out successfully" }

Changes to Program.cs:
  - Added DbSet<RevokedTokenModel> RevokedTokens to VaxtrackDbContext.
  - Registered ITokenBlacklistRepository as scoped.
  - Added JwtBearerEvents.OnTokenValidated hook:
      Resolves ITokenBlacklistRepository from request scope.
      Reads JTI from validated Principal.
      If IsRevokedAsync(jti) == true → context.Fail("Token has been revoked.")
      → request rejected with 401 before hitting any controller.

EF migration: AddRevokedTokensTable — applied to database.

TASK 8 — Forgot Password Flow (Gap 7)
────────────────────────────────────────────────────────────────────────────────

Problem:
  ChangePasswordAsync (Task 4) covers password rotation — the user is logged in
  and knows their current password. There was no path for a user who is locked
  out because they cannot remember their password at all.

Design:
  Two-step flow, both endpoints [AllowAnonymous] (caller is not logged in):

  Step 1 — POST /auth/forgotpassword
    User provides their email. System generates a 32-char hex token (GUID),
    stores it in a new PasswordResetTokens table with a 15-minute expiry,
    and returns it in the response.
    NOTE: in production this token would be sent via email and stripped from
    the response body. The field is exposed here only because there is no
    email service yet — a one-line change removes it once SMTP is wired up.

  Step 2 — POST /auth/resetforgottenpassword
    User provides the reset token + new password. System validates the token
    (must exist, not expired, not already used), BCrypt-hashes the new
    password, updates UserCredentials, and marks the token as used.

Security properties:
  - ForgotPasswordAsync always returns the same generic message regardless of
    whether the email is registered — prevents email enumeration.
  - Token is single-use: IsUsed is set to true before the password write,
    closing any race-condition replay window.
  - Token TTL is 15 minutes — short enough to limit exposure if intercepted.
  - No current password required — that is the entire point of this flow vs
    ChangePasswordAsync.

New files:
  Models/PasswordResetTokenModel.cs:
    Id, UserUid, Token, IsUsed, ExpiresAt, CreatedAt, UsedAt
  Interfaces/RepositoryInterfaces/IPasswordResetTokenRepository.cs:
    CreateTokenAsync(userUid, token, expiresAt)
    GetValidTokenAsync(token) → PasswordResetTokenModel?
    MarkTokenAsUsedAsync(tokenId)
  Repositories/PasswordResetTokenRepository.cs: full implementation
  Dtos/AuthDtos/ForgotPasswordRequestDto.cs: Email
  Dtos/AuthDtos/ForgotPasswordResponseDto.cs: Message, ResetToken?, ExpiresAt?
  Dtos/AuthDtos/ResetForgottenPasswordRequestDto.cs: ResetToken, NewPassword
  Dtos/AuthDtos/ResetForgottenPasswordResponseDto.cs: UserId, UpdatedAt

Modified files:
  Interfaces/IAuthService.cs             — added ForgotPasswordAsync,
                                           ResetForgottenPasswordAsync
  Services/AuthService.cs                — injects IPasswordResetTokenRepository;
                                           implemented both methods
  Controllers/AuthController.cs          — added ForgotPassword and
                                           ResetForgottenPassword endpoints
  Program.cs                             — registered IPasswordResetTokenRepository;
                                           added PasswordResetTokens DbSet

TASK 9 — Hospital-Admin Role: Gap Fix
────────────────────────────────────────────────────────────────────────────────

Context:
  The UserRoleMappings table supports scoped roles via (RoleTag, ContextId).
  A user with RoleTag = "hospital-admin" and ContextId = HospitalId manages
  that one specific hospital. However, no controller or service was checking
  for this role — it existed in the DB but was entirely inert. A hospital-admin
  was treated identically to a normal user.

Gaps fixed (4):
  1. ApproveBookingsAsync — was [Authorize(Roles="admin")], blocked hospital-admin.
     Now [Authorize]. Service checks: is the booking's pending dose at a hospital
     this caller manages? Dose 1 → Dose1HospitalUid, Dose 2 → Dose2HospitalUid.

  2. UpdateHospitalAsync — was admin-only. Now any authenticated user can call it;
     service checks hospital-admin role scoped to that HospitalId → 403 if not admin
     and not hospital-admin for that hospital.

  3. UpdateTotalSlotsAsync — same pattern as above.

  4. UpdateAvailableSlotsAsync — same pattern, BUT this method is also called
     internally by BookingService (slot reservation/release on create/cancel/delete).
     Those internal calls bypass the auth check via optional default params
     (callerIsAdmin = true). Controller calls always pass real caller values.

Authorization pattern used (consistent with ownership checks elsewhere):
  Service receives callerUserUid + callerIsAdmin from the controller.
  If callerIsAdmin → allow.
  Else → IUserRoleMappingRepository.IsUserInRoleAsync(callerUserUid, "hospital-admin", hospitalId).
  If false → throw UnauthorizedAccessException → controller returns 403 Forbid.

ContextId convention confirmed:
  HospitalId (readable PK) is used as ContextId in UserRoleMappings.
  This is consistent with DeleteHospitalAsync cascade (already used HospitalId)
  and with how bookings store Dose1HospitalUid / Dose2HospitalUid (which are
  HospitalId values despite the "Uid" name in the field).

Modified files:
  Interfaces/IBookingService.cs          — added callerUserUid + callerIsAdmin
                                           to ApproveBookingsAsync signature
  Services/BookingService.cs             — injected IUserRoleMappingRepository;
                                           added hospital-admin scoped check in
                                           ApproveBookingsAsync; restructured
                                           dose-selection logic into bool flags
                                           so the auth check targets the right hospital
  Controllers/BookingController.cs       — ApproveBookingsAsync: removed

                                           CallerUserUid/CallerIsAdmin, catches
                                           UnauthorizedAccessException → 403
  Interfaces/IHospitalService.cs         — added callerUserUid + callerIsAdmin to
