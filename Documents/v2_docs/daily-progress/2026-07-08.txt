────────────────────────────────────────────────────────────────────────────────

What was done:

  pages) were bolted on later in the week.

TASK 3 — Booking Lifecycle Expansion
────────────────────────────────────────────────────────────────────────────────

Problem:
  Only create/cancel/approve existed. Real usage needed: fixing a booking made
  for the wrong hospital/date, rebooking after a rejection, and giving admins/
  hospital-admins a trail of who did what to a booking.

What was done:
  New endpoints (BookingController / IBookingService / BookingService):
    - EditBookingAsync — owner can move an unapproved dose (1 or 2) to a new
      hospital/date. New DTO: EditBookingRequestDto (BookingId, UserUid,
      DoseNumber [1-2], NewHospitalUid, NewRequestedDateTime).
    - RebookDose1Async — re-creates dose 1 after it was cancelled/rejected,
      instead of forcing a brand-new booking record. New DTO:
      RebookDose1RequestDto (BookingId, UserUid, NewHospitalUid,
      NewRequestedDateTime).
    - RejectBookingsAsync — distinct from CancelBookingsAsync; admin/
      hospital-admin rejects a pending dose (semantically different from a
      user-initiated cancel, tracked separately in the audit trail).
    - GetBookingAuditTrailAsync — returns List<BookingAuditLogDto> (BookingId,
      DoseNumber, ActionType, ActorUserUid, ActorRole, Comment, CreatedAt).
    - GetActionableBookingsAsync — bookings still needing action, scoped to
      the caller's hospital-admin assignment(s) (or all, for platform admin).
    - GetNextAvailableSlotAsync — read-only preview of the slot a booking
      would get for a given hospital+date, used by the "my-bookings" UI to
      show an info card before the user submits.
  New model/table: BookingAuditLogModel + BookingAuditLogRepository —
    every dose-level action (create/approve/cancel/reject/edit/rebook) now
    writes an audit row.
  BookingActionCommentRequestDto — shared optional-comment body for
    Approve/Reject/Cancel so a remark can travel with the action.
  BookingProfileDataDto extended with Dose1DisplayStatus / Dose2DisplayStatus /
    VaccinationDisplayStatus (server-computed, so the UI stops re-deriving
    status from raw booleans) and Dose1HospitalAdminEmails /
    Dose2HospitalAdminEmails (comma-joined, for contact-info display).

Frontend:
  my-bookings.html/.ts grew substantially (798 lines added) to surface the
  full dose lifecycle: edit, rebook, cancel, approve/reject (for hospital-
  admin view), audit trail modal, next-available-slot preview card.
  New shared component: audit-trail (renders BookingAuditLogDto[] as a
  timeline, reused by both booking and hospital audit views).

TASK 4 — Hospital Lifecycle Management (Disable / Reactivate / Unregister)
────────────────────────────────────────────────────────────────────────────────

Problem:
  Hospitals could only be created and have their contact details/slots
  updated. There was no way to take a hospital offline, bring it back, or
  permanently remove one — and the earlier "delete hospital" contract was
  aspirational (no such endpoint ever existed in code).

Design — status field + two-party confirmation for unregister:
  HospitalModel gained Status ("Active" | "Disabled" | "PendingUnregister") and
  StatusComment. New HospitalAuditLogModel + HospitalAuditLogRepository track
  every lifecycle transition (ActionType, ActorUserUid, ActorRole, Comment).

  New endpoints (HospitalController / IHospitalService / HospitalService):
    - DisableHospitalAsync — platform admin only, reason required.
    - RequestReactivationAsync — the hospital's own hospital-admin asks to be
      re-enabled (comment optional).
    - ApproveReactivationAsync / RejectReactivationAsync — platform admin only.
    - RequestUnregisterAsync — platform admin only, reason required; puts the
      hospital in PendingUnregister.
    - WithdrawUnregisterRequestAsync — platform admin can back out.
    - DeclineUnregisterRequestAsync — the hospital's own hospital-admin can
      push back on a pending unregister.
    - AuthorizeUnregisterAsync — the hospital-admin re-enters their own login
      password (or the platform admin, if no hospital-admin is assigned) as a
      second-party confirmation before the hospital is permanently removed.
      New DTO: AuthorizeUnregisterRequestDto (Password, Comment).
    - GetHospitalAuditTrailAsync — full lifecycle history for one hospital.
  Shared DTO: HospitalActionCommentRequestDto (optional Comment) used across
    Disable/RequestReactivation/ApproveReactivation/RejectReactivation/
    RequestUnregister/WithdrawUnregister/DeclineUnregister.
  HospitalProfileDataDto extended with Status, StatusComment,
    HospitalAdminCount.

Frontend:
  New shared components: authorize-unregister-modal (password re-entry),
  hospital-audit-trail. hospital-list.html/.ts extended (554 lines) with the
  full status-driven action set (disable/reactivate/unregister buttons appear
  based on current Status + caller role) and later (0708) with extra filters
  and slot-adjustment controls.

TASK 6 — Hospital-Admin Applications + Notifications System
────────────────────────────────────────────────────────────────────────────────

Problem:
  Hospital-admin role assignment was admin-only (AssignRoleAsync) — there was
  no self-service path for a regular user to request that scoped role, and no
  in-app way to tell a user their request had been resolved.

What was done:
  New UserRequestModel + IUserRequestRepository — generic pending-request
  table backing two self-service flows (see also Task 7):
    - SubmitHospitalAdminApplicationAsync — a logged-in user applies to
      manage a specific hospital (HospitalId + optional Comment).
    - ApproveHospitalAdminApplicationAsync / RejectHospitalAdminApplicationAsync
      — platform admin resolves it; approval creates the underlying
      UserRoleMapping (hospital-admin, ContextId = HospitalId).
    - GetPendingRequestsAsync — admin's queue of all pending UserRequests
      (both request types).
  New NotificationModel + INotificationRepository + NotificationController —
    fire-and-forget notifications (NotifyAsync / NotifyAllAdminsAsync) fired
    alongside existing audit-log calls whenever something needs the user's or
    admins' attention (booking approved/rejected, hospital status changed,
    application resolved, etc.). Endpoints: GetMyNotificationsAsync,
    GetUnreadCountAsync, MarkAsReadAsync, MarkAllAsReadAsync.
  New IEmailService + SmtpSettings — groundwork for actually emailing reset
    tokens/notifications instead of just returning them in API responses
    (see forgot-password flow, logged 2026-06-25).

TASK 7 — Account-Disabled Login Block + Public Reactivation Request
────────────────────────────────────────────────────────────────────────────────

Problem:
  DisableUserAsync (Task 5) could flag an account, but LoginAsync never
  checked it — a disabled user could still log in and use the app normally.

What was done:
  - New AccountDisabledException(reason) — thrown by AuthService.LoginAsync
    only after password verification succeeds, never before, so a wrong-
    password guess can't be used to probe whether an account is disabled.
    AuthController catches it and returns 403 { code: "ACCOUNT_DISABLED",
    message, reason }.
  - New endpoint RequestAccountReactivationAsync (AllowAnonymous) — the only
    way back for a disabled user, since login itself is now fully blocked.
    Creates a UserRequestModel (RequestType = "AccountReactivation").
    New DTO: RequestAccountReactivationRequestDto (Email, Reason?).
  - Resolved via the same ApproveUserReactivationAsync/
    RejectUserReactivationAsync endpoints added in Task 5.

Frontend:
  New public route/feature: account-reactivation (reachable without a
  session, since a disabled account can never log in to reach it any other
  way) — surfaces the 403/ACCOUNT_DISABLED response from login and lets the
  user submit a reactivation reason directly.

TASK 8 — Vaccination Certificate Download/Share + Admin Filters
────────────────────────────────────────────────────────────────────────────────

What was done:
  - New endpoint GetCertificateAsync (BookingController, AllowAnonymous) —
    public, unauthenticated lookup by bookingId, mirroring how a real
    certificate's QR code works. New DTO: CertificateDto (BookingId,
    BeneficiaryName, BeneficiaryAge, BeneficiaryGender, Dose1HospitalName,
    Dose1CompletedDate, Dose2HospitalName, Dose2CompletedDate,
    VaccinationCompletedDate) — deliberately excludes email/phone/address,
    same restraint as a real printed certificate.
  - IUserRepository gained a lookup used to resolve beneficiary name/age/
    gender for the certificate without exposing the full UserProfileDataDto.
  - Frontend: new certificate.service.ts (142 lines) generates a downloadable
    certificate (client-side render) and a share link; new public route
    features/certificate-verify lets anyone holding the link verify a
    completed vaccination without logging in. my-bookings page gained a
    "Download certificate" / "Share" action once VaccinationDisplayStatus
    is "Vaccinated".
  - Admin screens (bookings-management, users-management, hospital-list) got
    additional filter controls (status/role/vaccination-status filters) on
    top of the paged-listing work from Task 5.
  - Support page updated to surface the hospital-admin application form
    (Task 6) alongside the existing delete-my-account flow.
