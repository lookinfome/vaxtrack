4. CONFIGURATION (appsettings.json)
================================================================================

Required sections:

  "ConnectionStrings": {
    "DefaultConnection": "Server=...;Database=VaxtrackDb;..."
  }

  "JwtSettings": {
    "Key": "<secret key, min 256-bit recommended>",
    "Issuer": "<issuer string>",
    "Audience": "<audience string>",
    "ExpiryMinutes": <int>
  }

JwtSettings is bound to a JwtSettings POCO model and registered as a singleton:
  var jwtSettings = builder.Configuration.GetSection("JwtSettings").Get<JwtSettings>()!;
  builder.Services.AddSingleton(jwtSettings);

The Key is used for HMAC-SHA256 signing. It must be kept secret and never
committed to source control in production.

6. AUTHENTICATION AND AUTHORIZATION DESIGN
================================================================================

Authentication mechanism: JWT Bearer tokens (stateless + blacklist hybrid).

Token validation parameters (Program.cs):
  ValidateIssuerSigningKey = true
  IssuerSigningKey         = HMAC-SHA256 from JwtSettings.Key
  ValidateIssuer           = true   (must match JwtSettings.Issuer)
  ValidateAudience         = true   (must match JwtSettings.Audience)
  ValidateLifetime         = true
  ClockSkew                = TimeSpan.Zero  (strict expiry, no buffer)
  RoleClaimType            = "role"         (custom claim name for ASP.NET role checks)

Authorization layers:
  Layer 1 — Middleware:
    [Authorize]              → must have valid JWT
    [Authorize(Roles="admin")] → JWT "role" claim must be "admin"

  Layer 2 — Controller helpers:
    CallerUserUid → User.FindFirst(JwtRegisteredClaimNames.Sub)?.Value ?? ""
    CallerIsAdmin → User.IsInRole("admin")
    Both passed to every service method that needs ownership/scope checks.

  Layer 3 — Service runtime check:
    if (!callerIsAdmin)
    {
        bool hasRole = await _roleMappingRepository.IsUserInRoleAsync(
            callerUserUid, "hospital-admin", entityId);
        if (!hasRole)
            throw new UnauthorizedAccessException(...);
    }
    Platform admin always bypasses this check.

  Layer 4 — Controller exception catch:
    catch (UnauthorizedAccessException) { return Forbid(); }  // 403

Token blacklist:
  OnTokenValidated event runs after signature validation on every request.
  It resolves ITokenBlacklistRepository from DI and checks IsRevokedAsync(jti).
  A match causes context.Fail("Token has been revoked") which returns 401.

Public (AllowAnonymous) endpoints:
  - POST /User/CreateUserAsync       (registration)
  - POST /Auth/LoginAsync
  - POST /Auth/ForgotPasswordAsync
  - POST /Auth/ResetForgottenPasswordAsync

7. JWT TOKEN DESIGN
================================================================================

Algorithm: HMAC-SHA256 (HS256)
Library:   System.IdentityModel.Tokens.Jwt (JwtSecurityTokenHandler)

Claims included in every token:
  Claim name | Claim value         | Notes
  -----------|---------------------|----------------------------------
  sub        | UserModel.UserUid   | GUID string, used for ownership checks
  email      | UserCredentials.Email|
  name       | UserModel.UserName  |
  role       | "admin" or "user"   | Drives [Authorize(Roles="admin")]
  jti        | Guid.NewGuid()      | Unique token ID for blacklisting

Scoped roles (hospital-admin) are NOT embedded in the token. They are looked
up in the DB at request time. This means:
  - Role assignment/revocation takes effect immediately on next request.
  - Token does not need to be reissued when scoped roles change.
  - Token size stays small regardless of how many scoped roles the user holds.

Token TTL: configurable via JwtSettings.ExpiryMinutes.
Logout: jti is blacklisted in RevokedTokens table. Token remains cryptographically
  valid but is rejected before hitting any controller.

8. PASSWORD SECURITY
================================================================================

Library:   BCrypt.Net-Next 4.0.3
Alias:     using BC = BCrypt.Net.BCrypt;

Operations:
  Hash:   BC.HashPassword(plainText)   → stored in UserCredentials.PasswordHash
  Verify: BC.Verify(plainText, hash)   → returns bool

Plain text passwords are NEVER stored, logged, or returned in any response.

Password change scenarios:
  A. ChangePasswordAsync (logged in, knows current password):
       - Non-admin: must verify CurrentPassword before hashing NewPassword.
       - Admin: bypasses current password check.

  B. ResetForgottenPasswordAsync (not logged in, has reset token):
       - No current password required; identity proven by token possession.
       - Token marked used before writing new hash (race-condition prevention).

Password is not validated for minimum complexity at the API level in v2.0.0.
That validation should be added in a future version.

9. SOFT-DELETE PATTERN
================================================================================

All entities use soft-delete. Records are never physically removed by the API.

Implementation per entity:
  Entity               | Soft-delete field | Timestamp field
  ---------------------|-------------------|----------------
  UserModel            | IsDeleted (bit)   | DeletedAt (datetime2?)
  UserCredentialsModel | IsDeleted (bit)   | DeletedAt (datetime2?)
  HospitalModel        | IsDeleted (bit)   | RemovedDate (datetime2?)
  BookingModel         | IsDeleted (bit)   | RemovedAt (datetime2?)
  UserRoleMappingModel | IsActive (bit)    | UpdatedAt (datetime2)
  RevokedTokenModel    | (no soft-delete;  | natural expiry only)
  PasswordResetToken   | IsUsed (bit)      | UsedAt (datetime2?)

Repository behavior:
  - All GetBy* methods include WHERE IsDeleted = 0 (or IsActive = 1).
  - Soft-deleted records do not appear in any lookup result.
  - Physical deletion is only possible via direct DB access.

Cascade delete behavior:
  User delete:    → Soft-deletes bookings, revokes role mappings, soft-deletes credentials.
  Hospital delete:→ Revokes all role mappings scoped to that hospital.
  Booking delete: → Restores pending slots to affected hospitals.

10. ID GENERATION PATTERN
================================================================================

UtilityService provides:

  GenerateGuidAsync():
    Returns Guid.NewGuid().ToString() (standard UUID format).
    Used for: UserUid, HospitalUid, BookingUid.
    Purpose: globally unique, collision-proof system identifier.

  GenerateUniqueIdAsync(seed):
    Returns a readable slug derived from the seed string.
    Pattern: {sanitized-seed}-{random-suffix}
    Used for: UserId (from FirstName), HospitalId (from HospitalName),
              BookingId (from "Book_{UserUid}").
    Purpose: human-readable primary key for API consumers.

Dual-ID pattern (every entity has both):
  Readable ID (string PK): returned in API responses, used in URL path params.
  GUID (string):           used as FK in related tables (links entities internally).

11. SLOT MANAGEMENT DESIGN
================================================================================

Hospital slot fields:
  TotalSlots     : maximum physical capacity. Admin-configurable.
  SlotsAvailable : real-time count of bookable slots.

Slot lifecycle:
  Event                         | Delta | Hospital field affected
  ------------------------------|-------|-------------------------
  User creates Dose1 booking    | -1    | Dose1Hospital.SlotsAvailable
  User creates Dose2 booking    | -1    | Dose2Hospital.SlotsAvailable
  User/admin cancels Dose1      | +1    | Dose1Hospital.SlotsAvailable
  User/admin cancels Dose2      | +1    | Dose2Hospital.SlotsAvailable
  Admin deletes booking (Dose1 pending) | +1 | Dose1Hospital.SlotsAvailable
  Admin deletes booking (Dose2 pending) | +1 | Dose2Hospital.SlotsAvailable
  Admin updates total slots (lower)     |    | SlotsAvailable clamped to new total

UpdateAvailableSlotsAsync takes a DELTA (not an absolute value).
  -1 = consume one slot.
  +1 = free one slot.

Guards:
  - newAvailable < 0         → throw (overbooking prevention).
  - newAvailable > TotalSlots → throw (cannot free more than capacity).

Internal vs external calls:
  - Controller calls pass real CallerUserUid + CallerIsAdmin for auth check.
  - BookingService internal calls use default optional params
    (callerUserUid="", callerIsAdmin=true) to bypass the auth check.
    These are system-driven adjustments, not end-user requests.

12. LOGGING DESIGN
================================================================================

Library: Serilog.AspNetCore + Serilog.Sinks.File

Configuration (Program.cs):
  MinimumLevel: Debug
  Override Microsoft.*: Warning (reduces ASP.NET framework noise)
  Override Microsoft.Hosting.Lifetime: Information (startup/shutdown visible)

Output template:
  {Timestamp:yyyy-MM-dd HH:mm:ss} [{Level:u3}] {Message:lj}{NewLine}{Exception}

Sinks:
  1. Console: real-time visibility during development and deployment.
  2. File: Logs/vaxtrack-{yyyy-MM-dd_HH-mm-ss}.log
           A new log file is created on every application start.

Logging pattern in services:
  _logger.LogError(ex, "ServiceName: MethodName - {Message}", ex.Message);

Every service and repository injects ILogger<T> via constructor.
Exception context (stack trace) is captured by Serilog's exception rendering.

Sensitive data (passwords, tokens) is never logged.

14. ERROR HANDLING PATTERN
================================================================================

Controller-level pattern:

  try
  {
      var result = await _service.MethodAsync(params);
      return Ok(result);  // or Created, NoContent
  }
  catch (UnauthorizedAccessException)
  {
      return Forbid();    // 403
  }
  catch (Exception ex)
  {
      _logger.LogError(ex, "ControllerName: MethodName - {Message}", ex.Message);
      return StatusCode(500, "An unexpected error occurred.");
  }

Service-layer pattern:

  try
  {
      // business logic
  }
  catch (UnauthorizedAccessException)
  {
      throw;  // let it bubble; controller catches → 403
  }
  catch (Exception ex)
  {
      _logger.LogError(ex, "...");
      throw new Exception($"ServiceName: Method - {ex.Message}", ex);
  }

ArgumentNullException.ThrowIfNull(param) is used before entering try blocks
to guard against null method arguments. This produces a clean ArgumentNull
exception which bubbles to the controller's generic catch → 500.

HTTP status codes used:
  200 OK         — Successful GET or PUT
  201 Created    — Successful POST (with Location header)
  204 No Content — Successful DELETE
  401            — Unauthenticated (handled by middleware, not controllers)
  403            — Unauthorized (Forbid())
  500            — Any unhandled exception

No 404 responses are currently returned; "not found" cases throw and
produce 500. This is a known simplification.

15. CORS POLICY
================================================================================

Applied globally via app.UseCors("AllowAll").

16. EF MIGRATIONS STRATEGY
================================================================================

Migrations are auto-applied on app startup:
  using (var scope = app.Services.CreateScope())
  {
      var dbContext = scope.ServiceProvider.GetRequiredService<VaxtrackDbContext>();

the schema stays in sync with the deployed code without a manual step.

Migration naming convention:
  Add{Feature}         — adds a new table or column
  Update_{TableName}   — modifies an existing table's structure

17. ROLE SYSTEM DESIGN (dual mechanism)
================================================================================

The system intentionally uses two separate, complementary role mechanisms:

MECHANISM 1 — PLATFORM ROLE (in JWT)
  Field:    UserModel.UserRole (bool)
  Values:   true = admin, false = user
  Baked into JWT at login: Claim("role", user.UserRole ? "admin" : "user")
  Evaluated by:
    - ASP.NET role authorization: [Authorize(Roles="admin")]
    - Controller helper: User.IsInRole("admin")
  Change requires:
    - DB update to UserModel.UserRole
    - User must log out and log in again to get a new JWT

MECHANISM 2 — SCOPED ROLE (in DB, runtime-checked)
  Table:    UserRoleMappings
  Fields:   UserUid, RoleTag, ContextId, IsActive
  Evaluated by:
    - Service-layer runtime query: IsUserInRoleAsync(userUid, roleTag, contextId)
  Change effect: immediate (next request hits the new DB state)
  No token reissue required.

Why two mechanisms?
  Platform admin is a global, long-lived privilege that warrants token inclusion.
  Scoped roles can be assigned and revoked frequently (e.g., hospital staff
  rotation). Embedding them in the JWT would require frequent token reissues
  or short TTLs. DB lookup at runtime is more flexible and immediately
  effective without client-side changes.

Currently supported roles:
  user          — default; baked into JWT
  admin         — platform-wide; baked into JWT
  hospital-admin — scoped to one hospital; in UserRoleMappings only

ContextId convention for hospital-admin:
  ContextId = HospitalModel.HospitalId (human-readable slug, not GUID).
  This matches the values stored in BookingModel.Dose1HospitalUid and
  Dose2HospitalUid, enabling direct comparison in ApproveBookingsAsync.
