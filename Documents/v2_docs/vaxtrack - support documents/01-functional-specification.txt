1. SYSTEM OVERVIEW
================================================================================

VaxTrack is a vaccination tracking backend API that manages the end-to-end
lifecycle of a two-dose vaccination program. It allows users to register,
book vaccination slots at hospitals, track dose completion, and manage their
profiles. Platform administrators manage hospitals and users. Hospital
administrators manage and approve bookings at their assigned facility.

Base URL pattern:
  /api/vaxtrack/v1/{Controller}/{Action}

All responses are JSON. All timestamps are UTC.

2. USER ROLES AND PERMISSIONS
================================================================================

The system uses two orthogonal role mechanisms:

A. PLATFORM ROLE (UserModel.UserRole — baked into JWT at login)
   - user  : Default role assigned on registration. Access limited to own data.
   - admin : Platform administrator. Full access across all entities.

B. SCOPED ROLE (UserRoleMappings table — checked at runtime per request)
   - hospital-admin : Scoped to a specific HospitalId (ContextId field).
                      Grants elevated access to that one hospital only.
                      Assigned and revoked exclusively by platform admins.

Role check behavior:
  - [Authorize(Roles = "admin")] on an endpoint: only JWT "role":"admin" passes.
  - Service-layer runtime check (IsUserInRoleAsync): queries UserRoleMappings
    table for the caller's UserUid, role tag, and relevant ContextId.
  - Platform admin bypasses all scoped role checks (callerIsAdmin = true skips
    the DB query entirely).

Permission matrix by role:
  Action                        | user | hospital-admin | admin
  ------------------------------|------|----------------|------
  Register                      |  Y   |      Y         |  Y
  Login / Logout                |  Y   |      Y         |  Y
  Forgot / Reset password       |  Y   |      Y         |  Y
  View own profile              |  Y   |      Y         |  Y
  Update own profile            |  Y   |      Y         |  Y
  Update own email              |  Y   |      Y         |  Y
  Change own password           |  Y   |      Y         |  Y
  Delete own account            |  Y   |      Y         |  Y

3. MODULE: AUTH
================================================================================

Base route: /api/vaxtrack/v1/Auth/{Action}

--------------------------------------------------------------------------------
3.1 LoginAsync
--------------------------------------------------------------------------------
Trigger       : User submits credentials to obtain a JWT token.
Auth required : None (AllowAnonymous).
HTTP method   : POST
Route         : /api/vaxtrack/v1/Auth/LoginAsync

Input (LoginRequestDto):
  Field     | Type   | Required | Notes
  ----------|--------|----------|----------------------------------
  Email     | string | Yes      | Registered email address
  Password  | string | Yes      | Plain text; verified against hash

Processing steps:
  1. Look up UserCredentials by Email.
  2. If not found or BCrypt.Verify(password, hash) = false → throw (generic).
  3. Look up UserModel by UserUid → if null or soft-deleted → throw (generic).
  4. Generate JWT with claims: sub=UserUid, email, name, role, jti (UUID).
  5. Token TTL set from JwtSettings.ExpiryMinutes (appsettings.json).

Output (LoginResponseDto):
  Field     | Type     | Notes
  ----------|----------|---------------------------
  Token     | string   | Signed JWT
  ExpiresAt | DateTime | UTC expiry of the token
  UserId    | string   | Human-readable user ID
  UserName  | string   | Full name
  Email     | string   | Registered email
  UserRole  | bool     | true = admin, false = user

Error cases:
  - Invalid email or wrong password → 500 (generic, no enumeration hint).
  - Soft-deleted account            → 500 (same generic message).

Constraints:
  - Same response message for all failure scenarios (enumeration prevention).

--------------------------------------------------------------------------------
3.2 LogoutAsync
--------------------------------------------------------------------------------
Trigger       : Authenticated user explicitly signs out.
Auth required : Any authenticated user (JWT bearer).
HTTP method   : POST
Route         : /api/vaxtrack/v1/Auth/LogoutAsync

Input: None (JWT must be in Authorization: Bearer header).

Processing steps:
  1. Extract jti and exp claims from already-validated Principal.
  2. Insert jti into RevokedTokens table with expiry timestamp.
  3. TokenBlacklistRepository opportunistically purges expired rows on insert.
  4. OnTokenValidated hook in Program.cs will reject this jti on future requests.

Output: { "message": "logged out successfully" }

Error cases:
  - Missing jti claim → 500.

Constraints:
  - Token is stateless but blacklisted; future requests with this token return 401.
  - Blacklist is periodically self-pruning (expired rows removed on each insert).

--------------------------------------------------------------------------------
3.3 ForgotPasswordAsync  (Step 1 of forgot-password flow)
--------------------------------------------------------------------------------
Trigger       : User cannot remember their password and requests a reset token.
Auth required : None (AllowAnonymous).
HTTP method   : POST
Route         : /api/vaxtrack/v1/Auth/ForgotPasswordAsync

Input (ForgotPasswordRequestDto):
  Field | Type   | Required | Notes
  ------|--------|----------|-------------------
  Email | string | Yes      | Account email

Processing steps:
  1. Look up UserCredentials by Email.
  2. If not found → return generic response (no token). Do NOT reveal absence.
  3. Look up UserModel by UserUid → if soft-deleted → same generic response.
  4. Generate token: Guid.NewGuid().ToString("N") — 32 hex chars.
  5. Set expiry = UtcNow + 15 minutes.
  6. Insert row into PasswordResetTokens table.
  7. Return token in response (dev/test only; omit once SMTP is wired up).

Output (ForgotPasswordResponseDto):
  Field      | Type      | Notes
  -----------|-----------|-------------------------------------------
  Message    | string    | Always the same generic message
  ResetToken | string?   | Token value (null if email not registered)
  ExpiresAt  | DateTime? | UTC expiry (null if email not registered)

Constraints:
  - Response is always identical in structure regardless of whether email exists.
  - Token expires in exactly 15 minutes from creation.
  - Token is single-use (IsUsed enforced in step 2 of the flow).

--------------------------------------------------------------------------------
3.4 ResetForgottenPasswordAsync  (Step 2 of forgot-password flow)
--------------------------------------------------------------------------------
Trigger       : User submits the reset token and their chosen new password.
Auth required : None (AllowAnonymous).
HTTP method   : POST
Route         : /api/vaxtrack/v1/Auth/ResetForgottenPasswordAsync

Input (ResetForgottenPasswordRequestDto):
  Field       | Type   | Required | Notes
  ------------|--------|----------|--------------------------------
  ResetToken  | string | Yes      | Token from step 1
  NewPassword | string | Yes      | Plain text; will be hashed

Processing steps:
  1. GetValidTokenAsync: query token where !IsUsed AND ExpiresAt > UtcNow.
  2. If not found → throw (invalid or expired).
  3. Look up UserCredentials by UserUid from token → if null → throw.
  4. Look up UserModel by UserUid → if null (deleted) → throw.
  5. MarkTokenAsUsedAsync BEFORE writing new hash (prevents race-condition replay).
  6. BCrypt.HashPassword(NewPassword) → UpdatePasswordHashAsync.
  7. Stamp UserModel.UpdatedAt = UtcNow.

Output (ResetForgottenPasswordResponseDto):
  Field     | Type     | Notes
  ----------|----------|-------------------
  UserId    | string   | Human-readable ID
  UpdatedAt | DateTime | UTC update time

Error cases:
  - Invalid token → 500.
  - Expired token → 500.
  - Already-used token → 500 (filtered out by GetValidTokenAsync).
  - User deleted since token was issued → 500.

4.1 CreateUserAsync  (Registration)
--------------------------------------------------------------------------------
Trigger       : New user registers on the platform.
Auth required : None (AllowAnonymous).
HTTP method   : POST
Route         : /api/vaxtrack/v1/User/CreateUserAsync

Input (CreateUserRequestDto):
  Field         | Type     | Required | Notes
  --------------|----------|----------|-------------------------------------
  FirstName     | string   | Yes      |
  LastName      | string   | Yes      |
  UserBirthdate | DateTime | Yes      | Must be in the past
  UserGender    | string   | Yes      |
  UserPhone     | string   | Yes      |
  UserAddress   | string   | Yes      |
  UserPinCode   | string   | Yes      |
  Email         | string   | Yes      | Must be unique across active accounts
  Password      | string   | Yes      | Plain text; BCrypt-hashed at storage

Processing steps:
  1. Validate UserBirthdate < UtcNow.
  2. Check if email is already in active UserCredentials → if yes, throw.
  3. Generate UserUid (GUID) and UserId (readable slug from first name).
  4. Calculate UserAge from birthdate via UtilityService.
  5. Insert UserModel with UserRole = false (regular user).
  6. BCrypt.HashPassword(Password) → insert UserCredentialsModel linked by UserUid.

Output (CreateUserResponseDto):
  Field     | Type     | Notes
  ----------|----------|----------------------
  UserId    | string   | System-generated ID
  UserName  | string   | FirstName + LastName
  Email     | string   |
  UserRole  | bool     | Always false
  CreatedAt | DateTime | UTC

Immutable at creation: UserId, UserUid, UserRole, UserAge, CreatedAt.

--------------------------------------------------------------------------------
5.4 UpdateAvailableSlotsAsync
--------------------------------------------------------------------------------
Trigger       : Admin or hospital-admin manually adjusts available slot count,
                OR BookingService internally calls this on booking create/cancel.
Auth required : Any authenticated user (controller); internal calls bypass auth.
HTTP method   : PUT
Route         : /api/vaxtrack/v1/Hospital/UpdateAvailableSlotsAsync/{hospitalId}/{slotsToUpdate}

Path params: hospitalId, slotsToUpdate (int, treated as DELTA not absolute).
  Pass -1 to consume a slot, +1 to free a slot.

Auth check: if !callerIsAdmin → hospital-admin check (same pattern).
  Internal BookingService calls use default params (callerIsAdmin=true) to
  bypass the check — these are system-driven, not user requests.

Processing:
  - newAvailable = SlotsAvailable + slotsToUpdate.
  - newAvailable < 0 → throw (over-booking prevented).
  - newAvailable > TotalSlots → throw (cannot free more than capacity).

Output: int (updated SlotsAvailable).

6. MODULE: BOOKING
================================================================================

Base route: /api/vaxtrack/v1/Booking/{Action}

Booking lifecycle state machine:
  Created (Dose1 pending) → Dose1 Approved → Dose2 Booked → Dose2 Approved
                                                              (VaccinationCompleted)
  At any pending state the dose request can be canceled.

--------------------------------------------------------------------------------
6.1 CreateBookingAsync  (Book Dose 1)
--------------------------------------------------------------------------------
Trigger       : User books their first vaccine dose.
Auth required : Any authenticated user; ownership enforced in service.
HTTP method   : POST
Route         : /api/vaxtrack/v1/Booking/CreateBookingAsync

Input (CreateBookingRequestDto):
  Field                 | Type     | Required | Notes
  ----------------------|----------|----------|------------------------------
  UserUid               | string   | Yes      | Must match JWT sub
  Dose1HospitalUid      | string   | Yes      | HospitalId of chosen hospital
  Dose1RequestedDateTime| DateTime | Yes      | Must be in the future
  Dose1SlotNumber       | int      | Yes      |

Processing:
  1. Verify createBookingRequest.UserUid == callerUserUid (anti-impersonation).
  2. Verify Dose1RequestedDateTime > UtcNow.
  3. Verify user has no existing active booking (one booking per user).
  4. Verify hospital has SlotsAvailable > 0.
  5. Create BookingModel with all Dose2 fields empty/false.
  6. UpdateAvailableSlotsAsync(Dose1HospitalUid, -1) to reserve the slot.

Output (CreateBookingResponseDto):
  BookingId, UserUid, Dose1RequestedDateTime, Dose1SlotNumber, Dose1HospitalUid.

Error cases:
  - UserUid in body != JWT sub → 403.
  - Past date → 500.
  - Duplicate booking → 500.
  - No slots available → 500.

--------------------------------------------------------------------------------
6.2 BookDose2Async
--------------------------------------------------------------------------------
Trigger       : User books their second dose after Dose 1 is administered.
Auth required : Any authenticated user; ownership enforced in service.
HTTP method   : PUT
Route         : /api/vaxtrack/v1/Booking/BookDose2Async

Input (BookDose2RequestDto):
  Field                 | Type     | Required | Notes
  ----------------------|----------|----------|----------------------
  BookingId             | string   | Yes      |
  Dose2HospitalUid      | string   | Yes      | HospitalId; may differ
  Dose2RequestedDateTime| DateTime | Yes      | Must be in the future
  Dose2SlotNumber       | int      | Yes      |

Processing:
  1. Verify Dose2RequestedDateTime > UtcNow.
  2. Look up booking; verify caller owns it.
  3. IsDose1Completed must be true.
  4. Dose2HospitalUid must be empty (not yet booked).
  5. IsDose2Completed must be false.
  6. Dose 1 must not be canceled.
  7. Verify Dose2 hospital has slots available.
  8. Set Dose2 fields; UpdateAvailableSlotsAsync(Dose2HospitalUid, -1).

Output (BookDose2ResponseDto):
  BookingId, UserUid, Dose2HospitalUid, Dose2SlotNumber,
  Dose2RequestedDateTime, IsDose2Completed.

--------------------------------------------------------------------------------
6.3 ApproveBookingsAsync
--------------------------------------------------------------------------------
Trigger       : Hospital staff confirms a dose was physically administered.
Auth required : Any authenticated user; role check in service.
HTTP method   : PUT
Route         : /api/vaxtrack/v1/Booking/ApproveBookingsAsync/{bookingId}

Path param: bookingId.

Processing:
  1. Find booking; verify not fully vaccinated.
  2. Determine which dose to approve:
     - approvingDose1: !IsDose1Completed AND !IsD1RequestCanceled.
     - approvingDose2: IsDose1Completed AND Dose2HospitalUid not empty
                       AND !IsDose2Completed AND !IsD2RequestCanceled.
  3. If neither condition met → throw (nothing to approve).
  4. Authorization check (if !callerIsAdmin):
     - Determine relevantHospitalId (Dose1 or Dose2 hospital).
     - IsUserInRoleAsync(callerUserUid, "hospital-admin", relevantHospitalId)
       must return true → else throw UnauthorizedAccessException.
  5. Approve the dose: set IsDose1Completed or IsDose2Completed = true,
     record timestamp. If Dose2 approved, also set IsVaccinationCompleted = true.

Output (BookingProfileDataDto): full booking state after approval.

Error cases:
  - Booking not found → 500.
  - Already fully vaccinated → 500.
  - No pending dose → 500.
  - Caller not admin and not hospital-admin for relevant hospital → 403.

--------------------------------------------------------------------------------
6.4 CancelBookingsAsync
--------------------------------------------------------------------------------
Trigger       : User cancels a pending dose, or admin cancels on their behalf.
Auth required : Any authenticated user; ownership enforced in service.
HTTP method   : PUT
Route         : /api/vaxtrack/v1/Booking/CancelBookingsAsync/{bookingId}

Ownership: caller must own booking or be admin.

Processing:
  1. Verify booking exists.
  2. Verify IsVaccinationCompleted = false.
  3. Priority logic:
     a. If !IsDose1Completed AND !IsD1RequestCanceled:
        → Set IsD1RequestCanceled = true; UpdateAvailableSlotsAsync(Dose1Hospital, +1).
     b. Else if IsDose1Completed AND Dose2HospitalUid not empty
           AND !IsDose2Completed AND !IsD2RequestCanceled:
        → Set IsD2RequestCanceled = true; UpdateAvailableSlotsAsync(Dose2Hospital, +1).
     c. Else → throw (nothing to cancel).

Output (BookingProfileDataDto): full booking state after cancellation.

Error cases:
  - Vaccination already completed → 500 (cannot undo administered vaccine).
  - Caller not owner → 403.
  - Nothing to cancel → 500.

7. MODULE: USER ROLE MAPPING
================================================================================

Base route: /api/vaxtrack/v1/UserRoleMapping/{Action}
All endpoints require admin role (class-level [Authorize(Roles = "admin")]).

--------------------------------------------------------------------------------
7.1 AssignRoleAsync
--------------------------------------------------------------------------------
Trigger       : Admin assigns a scoped role to a user.
HTTP method   : POST
Route         : /api/vaxtrack/v1/UserRoleMapping/AssignRoleAsync

Input (AssignRoleRequestDto):
  Field     | Type   | Required | Notes
  ----------|--------|----------|------------------------------------------
  UserUid   | string | Yes      | GUID of the target user
  RoleTag   | string | Yes      | e.g. "hospital-admin"
  ContextId | string | No       | e.g. HospitalId; empty = global scope

Processing:
  1. Verify user exists (GetUserDetailsByUserUidAsync).
  2. Check for existing mapping (same UserUid + RoleTag + ContextId):
     a. If active → throw (duplicate assignment prevented).
     b. If revoked (IsActive=false) → reactivate (set IsActive=true, UpdatedAt=now).
     c. If none → insert new row.

Output (AssignRoleResponseDto):
  Id, UserUid, RoleTag, ContextId, IsActive, CreatedAt.

--------------------------------------------------------------------------------
7.2 RevokeRoleAsync
--------------------------------------------------------------------------------
Trigger       : Admin removes a scoped role from a user.
HTTP method   : DELETE
Route         : /api/vaxtrack/v1/UserRoleMapping/RevokeRoleAsync/{mappingId}

Path param: mappingId (int, PK of UserRoleMappings).

Processing:
  1. Find mapping by Id → if not found, throw.
  2. If already inactive → throw (idempotency guard).
  3. Set IsActive = false, UpdatedAt = now.

Output: 204 No Content.
Role effect is immediate; next request from that user will fail the DB check.

================================================================================
8. GLOBAL CONSTRAINTS
================================================================================

- All timestamps are stored and returned in UTC.
- Soft-delete is used throughout; records are never physically removed by the
  API. Soft-deleted records are excluded from all future lookups.
- One active booking per user at a time (enforced by IsBookingExistsAsync check
  against UserUid in the Bookings table).
- UserAge is calculated once at registration and stored; not recalculated.
- Email must be unique across active UserCredentials rows.
- BCrypt is the only password hashing algorithm; plain text is never stored.
- JWT tokens are short-lived (ExpiryMinutes from config). Revoked tokens
  are tracked in RevokedTokens table and blocked on every authenticated request.
- HospitalId (readable slug) is used as the ContextId for hospital-admin
  role assignments, matching the Dose1HospitalUid/Dose2HospitalUid fields
  stored in BookingModel.
- Slot management is maintained as: SlotsAvailable always stays within
  [0, TotalSlots]. The API enforces both bounds.
- Hospital deletion is blocked if active bookings exist for that hospital.
- User deletion cascades to bookings and role mappings.

================================================================================
9. GLOBAL ASSUMPTIONS
================================================================================

- No email delivery service is currently integrated. Forgot-password reset
  tokens are returned in the API response for development purposes.
- UserAge is not recalculated over time; it reflects age at registration.
- ProfilePicturePath stores a path or URL string; image upload/serving is
  outside the scope of this API.
- The system does not enforce a minimum gap between Dose 1 and Dose 2 dates.
- Slot number (Dose1SlotNumber, Dose2SlotNumber) is caller-supplied; no
  server-side slot scheduling validation is performed.
- A hospital-admin is always scoped to exactly one hospital per role mapping.
  A user may hold hospital-admin for multiple hospitals via multiple rows.
- The RevokedTokens table is self-pruning; expired entries are deleted when
  a new revocation is inserted.

================================================================================
10. BUSINESS RULES SUMMARY
================================================================================

BR-01: A user cannot create a booking for another user.
BR-02: A user can only have one active booking at a time.
BR-03: Dose 1 must be approved before Dose 2 can be booked.
BR-04: Dose 2 can be at a different hospital than Dose 1.
BR-05: A dose that has been administered cannot be canceled.
BR-06: Canceling a pending dose restores one slot to the relevant hospital.
BR-07: Hospital-admin can only approve bookings at their assigned hospital.
BR-08: Hospital-admin can only update their assigned hospital.
BR-09: Platform admin can modify any entity without scoped role checks.
BR-10: Role assignment is reactivation-safe (no duplicate active rows).
BR-11: Deleting a hospital revokes all hospital-admin assignments for it.
BR-12: Deleting a user cascades to soft-delete their bookings and role mappings.
BR-13: Future birthdate is rejected at registration.
BR-14: An email must be unique across all active (non-deleted) accounts.
BR-15: Admin can change a user's email or password without the user's current password.
