================================================================================
  VAXTRACK — JWT AUTHENTICATION LAYER: IMPLEMENTATION PLAN
  Document Purpose: Complete walkthrough of every step taken to implement
  authentication and authorization in the VaxTrack ASP.NET Core 10 Web API.
  Covers what, why, how, and what breaks if the step is skipped.
================================================================================

BACKGROUND
----------
VaxTrack is a 3-layer ASP.NET Core 10 Web API (Controllers → Services →
Repositories) backed by SQL Server via EF Core 10. Before this auth layer,
all endpoints were open — anyone could read, create, update, or delete any
user, hospital, or booking without identifying themselves. This document
covers every step taken to close that gap using JWT (JSON Web Token) bearer
authentication and BCrypt password hashing.

The two authentication questions every secure API must answer:
  1. Who are you?       → Authentication  (JWT login flow)
  2. What can you do?   → Authorization   (role-based [Authorize] attributes)

STEP 1 — INSTALL REQUIRED NUGET PACKAGES
================================================================================

Packages added:
  • Microsoft.AspNetCore.Authentication.JwtBearer  (version 10.0.8)
  • BCrypt.Net-Next                                (version 4.0.3)

WHY JwtBearer?
  ASP.NET Core does not ship with JWT validation out of the box. The
  JwtBearer package wires into the ASP.NET Core authentication pipeline and
  gives us the middleware that reads the Authorization header, validates the
  JWT signature, checks expiry, and populates HttpContext.User so [Authorize]
  attributes work correctly.

WHY BCrypt.Net-Next?
  Passwords must NEVER be stored as plain text. BCrypt is a password-hashing
  algorithm designed to be intentionally slow (work factor / cost parameter),
  which makes brute-force attacks extremely expensive even if the database is
  compromised. BCrypt also embeds a random salt into every hash automatically,
  so two identical passwords produce different hash strings — preventing
  rainbow-table attacks.

  Why not SHA-256 or MD5?
    Those are general-purpose hash functions designed to be fast. Fast = bad
    for passwords. An attacker can run billions of SHA-256 guesses per second
    on commodity hardware. BCrypt's cost factor makes each verification
    milliseconds-slow by design.

WHAT BREAKS IF SKIPPED?
  • Without JwtBearer: [Authorize] attributes compile fine but always return
    HTTP 401 or simply do nothing depending on configuration. The middleware
    has no idea what a JWT is.
  • Without BCrypt: We'd have to store plain-text passwords or use a weaker
    hash. Either outcome is a critical security vulnerability.

STEP 2 — ADD JwtSettings TO appsettings.json
================================================================================

Section added to appsettings.json:
  "JwtSettings": {
    "Key": "<long-random-secret-string>",
    "Issuer": "vaxtrack-api",
    "Audience": "vaxtrack-client",
    "ExpiryMinutes": 60
  }

WHAT EACH FIELD DOES:

  Key (Secret)
    The cryptographic signing key. The API uses this key to sign the JWT when
    issuing it at login, and to verify the signature on every subsequent
    request. If the key doesn't match, the token is rejected.
    Must be long (32+ characters) and kept secret — never committed to a
    public repository in production. In production, use environment variables
    or a secrets manager (Azure Key Vault, AWS Secrets Manager, etc.).

  Issuer
    A string that identifies WHO issued the token (this API). Included in the
    token's payload. The middleware checks that incoming tokens declare the
    same issuer — prevents tokens issued by other services from being
    accepted.

  Audience
    A string that identifies WHO the token is intended for (the client app).
    Same purpose as Issuer but from the recipient's perspective. Both Issuer
    and Audience are standard JWT claims (iss / aud) defined in RFC 7519.

  ExpiryMinutes
    How long a token remains valid after issuance. After this window, the
    token is rejected even if the signature is valid. Short expiry (e.g. 60
    min) limits the damage window if a token is stolen. After expiry the user
    must log in again (or use a refresh-token flow, which is out of scope).

WHAT BREAKS IF SKIPPED?
  The JWT middleware configuration in Program.cs reads from this section.
  Without it, the middleware will be configured with null/empty values,
  causing every token validation to fail or the app to throw at startup.

STEP 3 — ADD Email AND PasswordHash FIELDS TO UserModel
================================================================================

Fields added to Models/UserModel.cs:
  public string Email        { get; set; } = "";
  public string PasswordHash { get; set; } = "";

WHY Email?
  Email is the login credential. Users identify themselves with an email +
  password pair at login. We need it stored on the user record so
  GetUserByEmailAsync can look up the account during login.

WHY PasswordHash (not Password)?
  The plain-text password is NEVER stored. When a user registers, the plain
  text is passed to BCrypt.HashPassword() and only the resulting hash string
  is persisted. At login, BCrypt.Verify(inputPassword, storedHash) is called —
  BCrypt extracts the salt from the stored hash and re-hashes the input for
  comparison. The original password is never recoverable from the hash.

  Naming the field PasswordHash (not Password) makes the intent explicit and
  prevents a future developer from accidentally assigning a plain-text value.

WHAT BREAKS IF SKIPPED?
  There is no identity for a user without Email. Login is impossible. The
  entire auth layer has no data to work with. Also: every user in the database
  would have no credentials — you'd have to rebuild registrations.

EF CORE MIGRATION REQUIRED:
  Adding these columns to the model doesn't change the database automatically.
  EF Core tracks model changes and requires an explicit migration command.
  See Step 9.

STEP 4 — ADD GetUserByEmailAsync TO IUserRepository AND UserRepository
================================================================================

Method added to Interfaces/RepositoryInterfaces/IUserRepository.cs:
  Task<UserModel?> GetUserByEmailAsync(string email);

Implementation in Repositories/UserRepository.cs:
  Queries the Users table for a non-deleted user whose Email matches the
  provided address (case-insensitive via EF Core's default SQL collation).
  Returns null if not found (nullable return type).

WHY?
  Login requires looking up a user by their email address, not by UserId or
  UserUid. Existing repository methods (GetUserDetailsByUserIdAsync) only
  query by the readable ID. This new method gives AuthService a way to find
  the account record needed to verify the password.

  The method filters out soft-deleted users (IsDeleted == false) — a deleted
  account should not be able to log in, even if the email/password are correct.

WHAT BREAKS IF SKIPPED?
  AuthService has no way to find a user during login. The login endpoint would
  always fail with "user not found" regardless of the credentials provided.

STEP 5 — UPDATE DTOs FOR EMAIL AND PASSWORD
================================================================================

Files changed and why:

  CreateUserRequestDto
    Added: Email (required), Password (required, min 8 chars)
    Why: Registration must capture credentials. These are validated by
    [Required] and [MinLength] attributes before the request even reaches the
    service layer. The Password field is plain text here — only ever exists
    in memory during the request lifetime; never persisted or logged.

  CreateUserResponseDto
    Added: Email
    Why: Confirm back to the caller what email was registered. Helps the
    client display a confirmation and detect accidental typos.

  UserProfileDataDto
    Added: Email
    Why: Profile views should show the user's login email.

  UserMasterDataDto
    Added: Email
    Why: Admin views of all users should include email for identification.

WHY NOT return PasswordHash in any DTO?
  The hash is an internal implementation detail. Returning it in any response
  leaks information that helps an attacker even if they can't reverse it
  (they can compare hashes across breaches to identify reused passwords).

WHAT BREAKS IF SKIPPED?
  Without Email on CreateUserRequestDto: registration doesn't capture the
  credential needed for login — user is created but can never log in.
  Without Password on CreateUserRequestDto: same; user registers but has no
  password hash stored.

================================================================================
STEP 6 — UPDATE UserService.MapUserCreateRequestToUserModel
================================================================================

Change in Services/UserService.cs:
  Email         = createUserRequestDto.Email,
  PasswordHash  = BCrypt.Net.BCrypt.HashPassword(createUserRequestDto.Password)

WHY here?
  The service layer is the correct place to apply business logic like password
  hashing before data reaches the repository. The repository's job is
  persistence — it should receive an already-prepared model, not raw
  credentials. Hashing in the service ensures the plain-text password never
  touches the database layer.

WHAT BREAKS IF SKIPPED?
  If hashing is omitted, PasswordHash is empty string. Every login will fail
  because BCrypt.Verify("anypassword", "") returns false. All previously
  registered users would need to re-register.

  If Email is not mapped, the field stays as empty string. GetUserByEmailAsync
  will never find the user.

STEP 7 — CREATE AUTH DTOs
================================================================================

New files:

  Dtos/AuthDtos/LoginRequestDto.cs
    Fields: Email (required), Password (required)
    Why: The login endpoint needs a strongly typed input. [Required] annotation
    ensures ASP.NET Core's model binding returns HTTP 400 automatically before
    AuthService is even called if either field is missing.

  Dtos/AuthDtos/LoginResponseDto.cs
    Fields: Token (JWT string), ExpiresAt (DateTime), UserId, UserName, UserRole
    Why: The login response must return the token the client will store and
    attach to future requests. ExpiresAt tells the client when to prompt for
    re-login. UserId and UserName allow the client to personalize the UI
    immediately after login without a separate profile call.

WHAT BREAKS IF SKIPPED?
  Without these DTOs, the auth controller has no typed model for its
  request or response — it would have to parse raw JSON manually, which is
  fragile and bypasses the validation pipeline.

STEP 8 — CREATE IAuthService AND AuthService
================================================================================

Interface: Interfaces/IAuthService.cs
  Task<LoginResponseDto> LoginAsync(LoginRequestDto loginRequest);

Implementation: Services/AuthService.cs

Login flow (what AuthService.LoginAsync does):
  1. ArgumentNullException.ThrowIfNull(loginRequest)  — guard before try block
  2. Look up user by email: _userRepository.GetUserByEmailAsync(loginRequest.Email)
  3. If user is null → throw "invalid email or password"
     (deliberately vague — never reveal whether the email exists)
  4. BCrypt.Verify(loginRequest.Password, foundUser.PasswordHash)
     If false → throw "invalid email or password"
  5. Build JWT claims:
       - sub    = foundUser.UserUid  (unique subject identifier)
       - email  = foundUser.Email
       - name   = foundUser.UserName
       - role   = foundUser.UserRole ? "admin" : "user"
       - jti    = Guid.NewGuid()     (unique token ID — prevents replay in logs)
  6. Sign token with the secret key from JwtSettings using HMAC-SHA256
  7. Return LoginResponseDto with token string, expiry, UserId, UserName, UserRole

WHY "invalid email or password" instead of "email not found"?
  Telling a caller "that email doesn't exist" is information leakage. An
  attacker can enumerate registered emails by observing which attempts get
  "email not found" vs "wrong password." A uniform error message reveals
  nothing about whether the account exists.

WHY store UserUid in the 'sub' claim (not UserId)?
  UserId is a readable, predictable string (e.g. "U001"). GUIDs are
  unguessable. The JWT subject should be an opaque identifier that cannot be
  enumerated. Controllers that need the readable UserId resolve it from the
  repository using the UserUid extracted from the token.

WHY HMAC-SHA256 (symmetric)?
  VaxTrack is a single-server API. Asymmetric signing (RS256) is beneficial
  when multiple separate services need to verify tokens independently without
  sharing a secret. For a single API that both issues and verifies its own
  tokens, symmetric HMAC-SHA256 is simpler, faster, and equally secure.

WHAT BREAKS IF SKIPPED?
  No login endpoint logic. Users have no way to obtain a token. The entire
  auth system is installed but non-functional — like putting a lock on a door
  with no key.

STEP 9 — CREATE AuthController
================================================================================

New file: Controllers/AuthController.cs

Endpoints:
  POST /api/auth/register  → calls UserService.CreateUserAsync
  POST /api/auth/login     → calls AuthService.LoginAsync

WHY a separate AuthController (not UserController)?
  Authentication is a cross-cutting concern, not a user management operation.
  Mixing login into UserController conflates two different responsibilities:
    • UserController  = CRUD on user profiles (requires auth)
    • AuthController  = identity verification (cannot require auth — it IS auth)

  A dedicated controller makes the separation clear and allows different
  middleware and routing rules to apply cleanly.

WHY is /register in AuthController and not UserController?
  Registration is the act of creating credentials (email + password), not just
  a profile. The same CreateUserAsync method is reused, but the endpoint lives
  in AuthController because:
    (a) It must be publicly accessible (no token needed to register)
    (b) It is semantically part of the identity flow, not profile management

WHAT BREAKS IF SKIPPED?
  No HTTP surface for login. Even with a perfect AuthService, there is no
  endpoint for the client to call to obtain a token.

STEP 10 — CONFIGURE JWT MIDDLEWARE IN Program.cs
================================================================================

Changes in Program.cs:
  1. Read JwtSettings from configuration
  2. Add authentication service:
       builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
         .AddJwtBearer(options => {
             options.TokenValidationParameters = new TokenValidationParameters {
                 ValidateIssuerSigningKey = true,
                 IssuerSigningKey         = new SymmetricSecurityKey(key),
                 ValidateIssuer           = true,
                 ValidIssuer              = jwtSettings.Issuer,
                 ValidateAudience         = true,
                 ValidAudience            = jwtSettings.Audience,
                 ValidateLifetime         = true,
                 ClockSkew                = TimeSpan.Zero
             };
         });
  3. Register IAuthService in DI:
       builder.Services.AddScoped<IAuthService, AuthService>();
  4. Confirm middleware ORDER (critical):
       app.UseAuthentication();   // must come before
       app.UseAuthorization();    // must come after

WHY ValidateLifetime = true AND ClockSkew = TimeSpan.Zero?
  ValidateLifetime ensures expired tokens are rejected. ClockSkew defaults to
  5 minutes in ASP.NET Core (to allow for slight clock drift between servers).
  Setting it to zero means a token expired 1 second ago is immediately invalid.
  For a single-server API this is the correct strict behavior.

WHY does middleware ORDER matter?
  UseAuthentication() reads the Authorization header, validates the JWT, and
  populates HttpContext.User with claims. UseAuthorization() then reads
  HttpContext.User to decide if the authenticated identity is allowed to access
  the requested resource. If they are reversed, UseAuthorization sees an empty
  HttpContext.User and denies every request.

WHAT BREAKS IF SKIPPED?
  If JwtBearer is not configured: tokens are generated at login but never
  validated — [Authorize] attributes are either non-functional or always deny.
  If IAuthService is not registered: the app throws
  InvalidOperationException at runtime when AuthController is first
  requested ("Unable to resolve service for type IAuthService").
  If middleware order is wrong: every protected endpoint returns HTTP 401
  regardless of whether the caller provided a valid token.

STEP 11 — ADD [Authorize] ATTRIBUTES TO CONTROLLER ENDPOINTS
================================================================================

Strategy applied:

  AuthController          → [AllowAnonymous] on both endpoints
                            (login and register must be publicly accessible)

  UserController          → [Authorize] at controller level
                            GetUserProfileDataAsync: [Authorize] (any logged-in user)
                            GetAllUsersAsync:        [Authorize(Roles = "admin")]
                            DeleteUserAsync:         [Authorize(Roles = "admin")]
                            UpdateUserAsync:         [Authorize] (user updates own profile)
                            CreateUserAsync:         Moved to AuthController as /register

  HospitalController      → [Authorize(Roles = "admin")] at controller level for
                            mutating endpoints (create, update, delete)
                            GetHospitalByIdAsync and GetAllHospitalsAsync:
                            [Authorize] (any logged-in user can browse hospitals)

  BookingController       → [Authorize] at controller level (all booking actions
                            require a logged-in user)
                            Approve actions: [Authorize(Roles = "admin")]

  UserRoleMappingController → [Authorize(Roles = "admin")] at controller level
                               (only admins manage role assignments)

WHY [Authorize] at the controller level as default?
  Applying [Authorize] at the top means every action is protected unless
  explicitly overridden with [AllowAnonymous]. This is a "secure by default"
  posture — a newly added endpoint is protected automatically. The alternative
  (decorating each action individually) is error-prone: a developer forgets
  one attribute and creates an unintended public endpoint.

WHY Roles = "admin" for destructive/administrative operations?
  The JWT token carries a "role" claim set to either "admin" or "user" based
  on UserModel.UserRole. [Authorize(Roles = "admin")] instructs the
  authorization middleware to reject requests where the role claim is "user".
  This prevents a regular user from deleting hospitals, approving bookings, or
  viewing all user records.

WHAT BREAKS IF SKIPPED?
  Without [Authorize]: all endpoints remain open — the entire JWT
  infrastructure is in place but never actually enforced. A regular user can
  delete hospitals. Anyone without a token can access any endpoint.
  Without [AllowAnonymous] on login/register: callers can never obtain a
  token in the first place — the login endpoint would return HTTP 401 because
  the caller has no token (chicken-and-egg problem).

STEP 12 — EF CORE MIGRATION: AddEmailAndPasswordToUsers
================================================================================

Commands run:
  dotnet ef migrations add AddEmailAndPasswordToUsers
  dotnet ef database update

WHAT THESE COMMANDS DO:

  dotnet ef migrations add AddEmailAndPasswordToUsers
    EF Core compares the current DbContext model (which now includes Email and
    PasswordHash on UserModel) against the last known migration snapshot. It
    generates a new C# migration file containing the SQL to add those two
    columns to the Users table. Nothing changes in the database yet.

  dotnet ef database update
    EF Core runs all pending migrations against the connected database,
    applying the generated SQL. The Users table now has Email and PasswordHash
    columns. Existing rows get the default value ("" empty string) for both
    columns — those accounts cannot log in and would need to re-register.

WHY generate a migration instead of directly editing the database?
  Migrations are code-tracked. They live in the repository alongside the model
  changes, so any developer cloning the repo can reproduce the exact database
  schema by running "dotnet ef database update." Manual SQL edits are
  invisible to EF Core's tracking and cause "model mismatch" errors.

WHAT BREAKS IF SKIPPED?
  The application throws at startup or on first database access:
  "Invalid column name 'Email'" / "Invalid column name 'PasswordHash'"
  EF Core tries to query/insert columns that don't exist in the database.
  The migration is NOT optional — the code change and database change must
  be applied together.

END-TO-END REQUEST FLOW AFTER AUTH LAYER IS IN PLACE
================================================================================

REGISTRATION (POST /api/auth/register)
  Client → AuthController → UserService.CreateUserAsync
    • Password is hashed via BCrypt before UserModel is saved
    • Email is stored on the user record
  Response: UserId, UserName, Email, UserRole, CreatedAt
  No token issued — user must login separately.

LOGIN (POST /api/auth/login)
  Client sends { "email": "...", "password": "..." }
  → AuthController → AuthService.LoginAsync
    • GetUserByEmailAsync finds the account
    • BCrypt.Verify checks the password against the stored hash
    • JWT is created with claims: sub, email, name, role, jti, exp
    • Token is signed with the secret key
  Response: { "token": "eyJ...", "expiresAt": "...", "userId": "...", ... }
  Client stores the token (typically in memory or secure storage).

AUTHENTICATED REQUEST (e.g. GET /api/user/profile)
  Client sends: Authorization: Bearer eyJ...
  → JwtBearer middleware intercepts the request BEFORE the controller
    • Reads the Authorization header
    • Validates signature, issuer, audience, and expiry
    • Populates HttpContext.User with the token's claims
  → [Authorize] attribute checks HttpContext.User.Identity.IsAuthenticated
    • If not authenticated → HTTP 401 Unauthorized (middleware short-circuits)
    • If authenticated → request reaches the controller action
  → Controller action proceeds normally

WHAT HAPPENS IF THE TOKEN IS EXPIRED?
  The middleware rejects it with HTTP 401. The client must call /login again
  to get a fresh token. No server-side session to invalidate — JWTs are
  stateless.

WHAT HAPPENS IF THE TOKEN IS TAMPERED WITH?
  The signature check fails. The middleware rejects it with HTTP 401.
  An attacker cannot forge a valid token without the secret key.

WHAT HAPPENS IF A "user" ROLE TOKEN HITS AN ADMIN-ONLY ENDPOINT?
  The role claim in the token is "user". [Authorize(Roles = "admin")]
  finds the role does not match. ASP.NET Core returns HTTP 403 Forbidden
  (distinct from 401 — the caller IS authenticated, but not authorized).

================================================================================
SECURITY NOTES FOR PROJECT REVIEWERS
================================================================================

1. Secret key management
   The JwtSettings.Key in appsettings.json is acceptable for local development
   and demo. In any production deployment it must be moved to environment
   variables, Azure Key Vault, or an equivalent secrets manager. The key should
   never appear in source control.

2. HTTPS
   JWT tokens in Authorization headers are plaintext-visible to anyone who can
   intercept network traffic. HTTPS (TLS) encryption is mandatory in production
   to protect tokens in transit. ASP.NET Core's default development setup
   includes HTTPS redirection.

3. Token revocation
   JWTs are stateless — there is no server-side session. If a token is stolen,
   it remains valid until expiry. Mitigation options (not implemented here):
     • Short expiry + refresh tokens
     • Token blacklist stored in Redis (checked on each request)
     • Rotating signing keys
   For a backend API demo, short ExpiryMinutes is the primary mitigation.

4. Password policy
   [MinLength(8)] on the Password field is the minimum. Production systems
   typically enforce complexity rules (uppercase, digit, special character)
   via a custom validation attribute or a library like FluentValidation.

5. Email uniqueness
   A unique constraint on the Email column in the database (added via a
   HasIndex().IsUnique() configuration in ApplicationDbContext or via
   migration) prevents two users registering with the same email. Without it,
   GetUserByEmailAsync would throw if it found multiple rows (or return the
   wrong user silently depending on implementation). This is an additional
   hardening step beyond the core auth flow.
